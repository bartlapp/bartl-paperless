# Bartl Paperless service

This package operates one isolated Paperless-ngx service with PostgreSQL 17.6, Redis, native documents, media, search index and OIDC. It does not provision or reset Keycloak, mail transport, a TLS gateway or a Restic repository. A supervisor owns the database and media transition and starts the exact rootless Granian, Celery worker, Celery beat and document-consumer commands used by upstream's s6 service definitions; `/init` itself requires PID 1 and cannot run as its child. No upstream product code is changed. The selected profile is private, one-node, one-replica Kubernetes; independently reachable services, protected credentials, persistent volumes, sufficient capacity and the selected Restic repository are target prerequisites.

## Build and inputs

`./build-runtime.sh 3.3.0 LOCAL_TAG` or `./build-runtime.sh 3.3.1 LOCAL_TAG` builds a local amd64 image from the exact supported upstream digest, adding the lifecycle supervisor, PostgreSQL 17 dump/restore clients and the qualified records XML parser. It does not publish images. Load the image into the target runtime and put its immutable digest in `images.runtime`. The image embeds the upstream release and digest; startup rejects a mismatch. `images.paperless` must match the selected 3.3.0 or 3.3.1 upstream digest pinned by the build script; [example-settings.json](example-settings.json) shows 3.3.0. PostgreSQL, Redis, Tika and Gotenberg keep their exact pins. No upstream Paperless code is changed.
On the selected K3s target, load and bind the exact local result before setting `images.runtime`:

```sh
./build-runtime.sh 3.3.0 bartl-paperless-native:3.3.0
image_ref=$(docker image inspect --format '{{index .RepoDigests 0}}' bartl-paperless-native:3.3.0)
docker save bartl-paperless-native:3.3.0 | k3s ctr images import --all-platforms -
k3s ctr images tag docker.io/library/bartl-paperless-native:3.3.0 "docker.io/library/$image_ref"
```

The build output is Docker's local image ID, not the registry manifest digest. The commands above use the actual repository digest for the illustrated local image name. The derived digest changes when supervisor or records profile bytes change; update service settings before provisioning a new generation. Never silently replace a digest already bound to established state.

`SETTINGS_JSON` supplies a unique DNS-safe `generation`, explicit `intent` (`fresh` or `recovery`), `identity` (`issuer`, `paperless`, `realm`, browser `client`, `provider: keycloak`), `initialization` (`database: postgresql-17`, `stateFormat: 1`, OCR and timezone), `versions.paperless`, the Paperless, PostgreSQL, Redis, Tika, Gotenberg and derived runtime image references, and optional `placement.identityIP`. `identity.issuer` and `identity.paperless` may use HTTP in the private proof or HTTPS with a separate trusted TLS gateway. The native upstream port is loopback-only inside the pod; the supervisor derives Host and forwarded scheme from the configured URL and overwrites untrusted forwarded headers. Restrict cluster backend ingress to the gateway and explicitly authorized lifecycle/probe callers before exposing HTTPS.
HTTPS mode supplies `PAPERLESS_PROXY_SSL_HEADER` as the native JSON array `["HTTP_X_FORWARDED_PROTO", "https"]`; a comma-separated string is not a valid Paperless setting.

`SECRET_DIR` contains protected `db-password`, `paperless-key`, `client-secret` and `records.json`. The records profile has `format: 1` and three distinct accounts: `records-intake`, `records-capture` and `records-admin`, each with a 32+ character password and its own 40-hex API token. Retain identical input bytes for restart and reconstruction. The supervisor rotates a dedicated native PostgreSQL writer credential per invocation. Native subprocesses receive their writer credential, Paperless key and scoped records secret, never the database owner password or Kubernetes API token. Under the same persistence lock, native `manage.py shell` initializes the records profile only during authorized fresh initialization and checks it before each accepted start.

## CLI

```sh
./bartl.sh validate SETTINGS_JSON SECRET_DIR [PAYLOAD_DIR]
./bartl.sh deploy SETTINGS_JSON SECRET_DIR [PAYLOAD_DIR]
./bartl.sh start SETTINGS_JSON SECRET_DIR
./bartl.sh stop SETTINGS_JSON SECRET_DIR
./bartl.sh capture SETTINGS_JSON SECRET_DIR NEW_DIR
./bartl.sh backup SETTINGS_JSON SECRET_DIR
./bartl.sh restore RECOVERY_SETTINGS_JSON SECRET_DIR EXACT_64_HEX_SNAPSHOT_ID
./bartl.sh reconcile SETTINGS_JSON SECRET_DIR CURRENT_DECISIONS_JSON
```

Run on an authorized target with Bash, jq, sha256sum, flock, OpenSSL, kubectl and Helm 4.3; building also needs Docker/buildx. `KUBECONFIG` defaults to `/etc/rancher/k3s/k3s.yaml`. `validate` checks inputs and ownership without creating resources. `deploy` initializes a confirmed empty owned target or resumes a bound operation; `start` explicitly resumes a stopped accepted installation. A recovery `deploy` takes a complete selected payload in `PAYLOAD_DIR`, and `restore` retrieves that payload by exact snapshot ID from the configured Restic repository before invoking the same state path. Set `RESTIC_REPOSITORY` (or `RESTIC_REPOSITORY_FILE`) and a supported Restic password reference for `backup`/`restore`. Neither action initializes, forgets, prunes or deletes the repository. `backup` returns `{"snapshot_id":"..."}` after capture, source restart and Restic upload. `capture` leaves the source stopped. Store capture directories and keys separately and protect them from modification.

The coordinator checks namespace ownership, observes an empty physical database/media/broker target, and retains its target identifiers and installation identity independently before granting fresh/recovery initialization authority. Inside the runtime, a state-volume file lock and PostgreSQL advisory lock enclose observation and mutation; the native process inherits the file-lock descriptor while serving. A dedicated non-superuser writer role is fenced (`NOLOGIN`, old backends terminated) and receives a fresh per-process credential only after state classification. Database system identifier, database OID, writer role OID, installation ID, the independent allocation, native migration graph (including squashed ancestors), media directories and broker-volume installation marker must agree. An established empty, partial, foreign or unavailable state is never treated as fresh. Native Django migration, index and sanity commands are used; no table drop/reset path exists. An interrupted partial restore visibly refuses further service and requires a new authorized empty target rather than overwriting unverified data. Supported transitions are 3.3.0 to 3.3.0/3.3.1 and 3.3.1 to 3.3.1 only.

The image embeds `native-profiles.json` with per-release full schema fingerprints from separate freshly native-migrated Paperless 3.3.0 and 3.3.1 installations on PostgreSQL 17.6. It also binds the exact dump/restored representation: PostgreSQL deparses one equivalent native MFA partial-index predicate differently after restore, although all other qualified columns, relations, constraints and index definitions match. Neither representation includes physical OIDs or column positions. Fresh initialization requires its fresh profile; selected restore requires its restored profile before media promotion; established restarts require one qualified profile, the retained hash and the full native migration history.
The qualified catalogue includes typmod-aware column types, named collation, nullability, defaults, identity/generated metadata, relation persistence and RLS flags, validated constraints, complete valid/ready index definitions and static sequence configuration. The measured native witnesses contain no application routines, user triggers, rewrite rules, policies or custom scalar types, so those classes are explicitly refused, as are foreign servers, event triggers, publications, subscriptions and large objects.

Paperless intake is proxied through the supervisor. Capture first fences new requests, waits for proxied in-flight requests and native pending/started tasks to settle, then stops and waits for all native pods. It rejects unsettled or unknown Redis keys after stop, stops Redis, runs native records/sanity/index checks, and only then seals one PostgreSQL custom dump with `data`, `media`, `consume` and the durable Redis append-only volume. The manifest, DB and file archive have explicit checksums; a selected restore checks them before mutation. Stateless Tika and Gotenberg converters are pinned dependencies and are not in the captured point. An external intake, mail system, or records ledger that bypasses the supervisor must be independently fenced and reconciled; this bounded deployment does not authorize mail cutover or real records import.

The `reconcile` action accepts a protected current decisions JSON bound to the service identity. It fences intake, drains native work, then runs the fixed native records reconciliation script under the same database and media lifecycle authority. Only after residue checks and native sanity succeed does it resume a previously running source; a stopped source stays stopped. The JSON receipt binds the installation, settings and decision digest. A failed reconciliation leaves the source stopped for inspection.
Failed native records helpers retain mode-600 stdout/stderr under `data/records-operations/failure-*.stdout` and `.stderr`; public failure output identifies only the exit status and protected diagnostic path. Retrying the same decision bytes preserves its journal and staged input; different bytes are refused until the unresolved operation is inspected. All operations use the declared runtime image. A corrected runtime is exercised on a new recovery generation, not substituted beneath an established contract.

Before serving, the runtime observes the complete native migration history and physical schema, checks document/file consistency and the exact records profile, verifies the configured OIDC issuer and converter endpoints, and exercises authenticated native document endpoints with all three records tokens. It emits JSON state/refusal/acceptance records; the CLI checks a live supervisor-only acceptance endpoint bound to the retained installation and release. Readiness alone is not service acceptance. Browser/OIDC and records-role behavior require integrated proof; TLS and production suitability require separate evidence.
